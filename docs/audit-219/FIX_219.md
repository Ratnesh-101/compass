## 2. Detailed Bug Fixes & Code Changes

### BUG-01: ReDoS Quadratic Backtracking in `_CREATION_PHRASE`
- **File**: [`backend/services/task_intent.py`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/services/task_intent.py#L43-L73)
- **Problem**: `_CREATION_PHRASE` combined a verb group with `.*` and a noun group under `re.DOTALL`. Repeating `"add "` or `"create "` on 50,000 characters caused polynomial catastrophic backtracking (>12,000 ms).
- **Solution**: Replaced the regex with `_LinearCreationPhraseMatcher` wrapping two distinct atomic expressions (`_CREATION_VERB` and `_CREATION_NOUN`). It searches for the first verb, then searches from the verb end position for any subsequent noun within an input truncated to 2,000 characters.
- **Audit Test**: `tests/test_audit_redos.py` ran in `0.00s` (<1 ms).

### BUG-03, BUG-04, BUG-08 & Quoted Speech Intent Classification
- **Files**: [`backend/services/task_intent.py`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/services/task_intent.py#L75-L195), [`backend/router_helpers.py:139`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/router_helpers.py#L139)
- **Problem**: 
  - Past inquiries ("Did you remind me...") and advice inquiries ("Should I add a task...", "Do you think I should add a task...") were extracting words as task titles and classifying as `COMMAND`.
  - Hinglish capability asks ("kya tum add task kar sakte ho" with or without `?`) extracted Hindi verbs ("Kar sakte ho") as task titles.
  - Quoted commands embedded within conversation (`He told me "remind me to call mom tomorrow" during lunch`) matched internal phrases and routed to `add_task`.
- **Solution**:
  - Implemented `_has_non_command_lead` using string splits to identify interrogative leads (`did`, `do/does` + pronoun, `should`, `is/are/am/was/were`, `why`, `how`, `what`, `kya`, `kaise`, `kyun`, and `can/could/would` + `i/we`). These always classify as `QUESTION` and block task creation.
  - Implemented `_strip_quoted_text` and `_has_command_in_quotes_only` to verify quote depth. When task creation phrases occur exclusively inside quotation marks while outer conversational text exists, task creation is blocked.
  - Added Hindi tokens (`kar`, `karna`, `sakte`, `sakta`, `sakti`, `ho`, `hain`, `tum`, `aap`, `kya`, `kaise`, `kyun`) to `_FILLER_WORDS` so non-English capability terms cannot form valid task titles.
  - Updated [`backend/router_helpers.py:139`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/router_helpers.py#L139) to check `blocks_task_creation(message)` unconditionally rather than requiring a trailing `?`.
- **Audit Test**: `tests/test_audit_intent.py` (4/4 tests passed).

### BUG-09: Unvalidated Raw Timezone Leaked in `format_due_label`
- **File**: [`backend/services/task_time.py:111-113`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/services/task_time.py#L111-L113)
- **Problem**: `format_due_label` evaluated `ZoneInfo(pick_timezone(tz_name, None))` for time conversion (falling back to UTC), but interpolated the raw unvalidated `tz_name` parameter into the return string, causing `"Mars/Phobos"` or 10 KB strings to leak into the user label.
- **Solution**: Assigned `valid_tz = pick_timezone(tz_name, None)` and interpolated `({valid_tz})`.
- **Audit Test**: `tests/test_audit_timezone.py` tests for invalid and oversized timezones pass.

### BUG-10: Frontend Request ID Omission & Intake Double-Click Race
- **Files**: [`frontend/src/api/chatApi.js:13,27,32`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/frontend/src/api/chatApi.js#L13-L32), [`frontend/src/components/chat/IntakePreviewCard.jsx`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/frontend/src/components/chat/IntakePreviewCard.jsx)
- **Problem**:
  - `sendQueryToAssistant` invoked `chatRequestFields()` with no `requestId`, omitting `request_id` from non-streaming chat turns and disabling idempotency.
  - `IntakePreviewCard` lacked disabled state on Confirm and Cancel buttons, permitting concurrent duplicate submissions.
- **Solution**:
  - Imported `makeRequestId` and passed `requestId || makeRequestId()` to `chatRequestFields` in `sendQueryToAssistant`.
  - Added `busy` state via `useState(false)` in `IntakePreviewCard.jsx`, wrapping `onConfirm` and `onCancel` with `setBusy(true)` / `finally setBusy(false)`, and set `disabled={busy}` on both buttons.
- **Audit Test**: `frontend/tests/audit-frontend.test.mjs` (2/2 passed).

### BUG-05: Oversized `request_id` Idempotency Bypass
- **File**: [`backend/services/chat_idempotency.py:12,33-46`](file:///C:/Users/Ratnesh%20Singh/OneDrive/Desktop/compass-chat-task-intake/backend/services/chat_idempotency.py#L33-L46)
- **Problem**: `normalize_request_id` returned `None` for IDs > 64 chars, causing `run_chat_request` to drop idempotency tracking and execute duplicate mutations on retries.
- **Solution**: If `len(val) > 64`, deterministically hash the value using SHA-256 to `f"req_{hashed[:40]}"` (44 chars), which fits safely in `REQUEST_ID_PATTERN` and retains tenant-scoped idempotency.
- **Audit Test**: `test_oversized_request_id_silently_bypasses_idempotency` passed.

### Root Cause Analysis
1. `structured.create_task` runs in its own dedicated connection/transaction inside `backend/orchestrator.py:760-800`.
2. `chat_request_log` record state updates take place inside `_finish` in `backend/services/chat_idempotency.py:113-128`.
3. When post-creation operations (such as formatting or logging) throw an exception, `handle_message` exits prematurely. `run_chat_request` executes `finally: await _finish(..., result=None)`.
4. In `_finish`:
   ```python
   else:
       await conn.execute(
           "DELETE FROM chat_request_log WHERE owner_identity = $1 AND request_id = $2",
           owner, request_id,
       )
   ```
   The pending claim is purged from `chat_request_log`, but the inserted row in `tasks` remains committed.
5. On client retry with the identical `request_id`, the request is treated as brand new. It attempts to create the task again and fails with `duplicate_exact_deadline`.

### Minimal Change Designs
- **Option 1 (Same-Transaction Write)**: Pass an active transaction context through `handle_message` into `create_task` and commit both `tasks` insertion and `chat_request_log` transition to `'done'` in the exact same transaction block. If formatting fails, the task mutation rolls back; if it commits, the idempotency record commits atomically.
- **Option 2 (Catch Duplicate on Retry & Replay)**: In `orchestrator.py` or `add_task` handler, if `structured.create_task` returns `error == "duplicate_exact_deadline"` and the caller provided a `request_id`, check if an identical task was created by the same user within the last 5 minutes. If found, format it as a successful replay instead of failing.

### Reason for Not Implementing
`backend/orchestrator.py` currently has 1,103 lines (a grandfathered file strictly capped and audited by `scripts/check_file_sizes.py`). Any unified transaction handling or duplicate recovery in `orchestrator.py` requires restructuring cross-module transaction lifetimes across `db.py` (which is at its hard 700-line ceiling), `structured.py`, and `chat_idempotency.py`. This exceeds the 40-line diff budget and touches files at their hard size limit. Per instructions, it is documented here and left uncommitted.
